# 검색 근거 검토 대시보드 UX 분석 및 개선 기획

작성일: 2026-09-09 · 대상: `/observability`

## 1. 결론과 검토 범위

현재 화면은 검색과 근거 분류 기록을 보여 주고 연구자 평가를 저장하는 초기 운영 화면이다. 검색의 정확성을 증명하는 평가 시스템은 아직 아니다. 사용자가 불편함을 느끼는 핵심 이유는 **어떤 검색을 보고 있는지, 이 수치로 무엇을 판단할 수 있는지, 다음에 무엇을 해야 하는지가 연결되지 않기 때문**이다. 제작자의 이해 수준은 판단할 수 없지만, 화면 용어와 실제 구현의 범위가 일치하지 않는 부분은 확인했다.

화면 컴포넌트, 스타일, API 경로, 집계 서비스, 규칙 기반 분류기, 저장소를 검토했다. 실제 API의 현재 응답은 `gapId: null`이며 검색·근거·평가 데이터가 없다. 내장 브라우저 연결이 불가능하여 스크린샷 기반 시각 검토와 실제 클릭·모바일 사용성 검증은 수행하지 못했다. 데이터가 있는 상태의 분석은 코드 경로를 근거로 한다. 실사용 테스트 결과로 해석하면 안 된다.

접근성·탐색·상태 안내 검토는 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)를 참고했다.

## 2. 실제 기능과 표시의 차이

| 영역 | 현재 실제 동작 | 사용자가 오해하기 쉬운 점 |
|---|---|---|
| 대상 검색 | 가장 최근 생성한 연구 주제를 선택하고 그 주제의 최근 검색 결과를 집계 | 가장 최근 성공한 검색을 보여 주는 것이 아니다. 주제·실행 선택 기능이 없다. |
| 검색 논문 수 | 최근 검색에 저장된 결과 수 | 전체 학술 데이터베이스의 검색 총량·정확도·재현율이 아니다. |
| 근거 수 | 해당 주제에 연결된 근거 레코드 수 | 최근 검색 결과와 집계 범위가 다를 수 있다. 중복 제거된 논문 수라는 보장도 없다. |
| 검색어 수정 | 수정 검색어 필드가 있는 실행 수 집계 | 자동 검색어 수정 실행기는 아직 없으며, 재정렬 수·수정 후 새 근거 수는 항상 미집계다. |
| 조건별 근거 | 조건과 제목·초록의 단어가 겹치는지 확인 | 조건을 의미적으로 충족한다는 검증이 아니다. 한국어 조건과 영어 논문 사이의 일치도 보장하지 못한다. |
| 반대 근거 | 직접·부분 중복으로 분류된 논문을 후보로 지정 | 논문 주장 사이의 반박 관계를 확인한 것이 아니다. 연구 공백의 존재를 반박할 가능성이 있는 후보다. |
| 자동 분류 요약 | 중복 등급과 역할을 문자열로 조합 | 원문에 근거한 독립적인 인공지능 주장 추출 기능이 아니다. |
| 수집 문장 | 초록 앞 900자, 초록이 없으면 제목 | 전체 논문 본문에서 검증에 필요한 구절을 추출한 것이 아니다. |
| 인용·원문 검증 | 세 상태 모두 `not_verified` 고정 | 검증기가 실행되어 불확실 판정을 내린 것이 아니다. |
| 판단 기록 | 저장된 판단 레코드 목록 + 마지막 연구자 결정 | 과거 각 판단과 당시 연구자 결정이 정확하게 연결된 이력이 아니다. |
| 연구자 평가 | 관련성·근거 관계를 새 레코드로 저장 | 수정 저장이 아닌 누적 추가다. 현재 평가값 조회·수정·평가자 구분·합의 확정 기능이 없다. |
| 품질 지표 | 11개 지표를 값 없이 표시 | 재현율·정밀도·순위 품질 등의 계산은 아직 없다. |
| 저장 | 프로세스 메모리의 딕셔너리 | 서버 재시작 후에도 보존되는 저장소가 아니다. |

## 3. 주요 문제와 코드 근거

### 우선순위 0: 기록의 범위와 신뢰성

- `services/api/app/services/observability_service.py:23` — 최신 생성 주제를 선택하므로 신규 빈 주제가 이전 성공 검색을 가린다. 실행 선택과 실행 식별자가 필요하다.
- `services/api/app/services/observability_service.py:58` — 연구자 평가 목록을 주제별로 제한하지 않는다. 현재 주제의 논문 목록 옆에 전체 주제 평가 건수가 표시될 수 있다.
- `services/api/app/services/observability_service.py:121` — 근거가 조건을 하나도 맞추지 못했는지를 검사한다. 모든 조건 중 미충족 조건이 있는지 검사하는 것과 다르다. 예: 모든 논문이 조건 A만 맞추고 조건 B는 아무도 충족하지 않아도 부족을 놓칠 수 있다.
- `services/api/app/services/observability_service.py:158` — 인용 일치·원문 뒷받침·근거 없는 주장 여부는 실제 검증 없이 고정된 미검증 값이다.
- `services/api/app/services/observability_service.py:177` — 존재 여부 판단에는 해당 주제의 모든 근거 ID를 연결하고 나머지 판단에는 빈 목록을 연결한다. 정확한 판단별 출처 추적으로 보기 어렵다.
- `services/api/app/repositories/in_memory.py:190` — 메모리 저장소만 사용한다. 지속적 평가 자료 축적의 선행 조건은 영구 저장이다.

### 우선순위 1: 사용 흐름

- `apps/web/features/observability/ObservabilityDashboardPage.tsx:29` — 메뉴 상태가 컴포넌트 상태에만 있어 새로고침·공유 시 선택 메뉴가 보존되지 않는다.
- `apps/web/features/observability/ObservabilityDashboardPage.tsx:70` — 평가 저장 성공 뒤 최신 대시보드를 다시 조회한다. 다른 최신 주제가 생기면 검토 대상이 바뀔 수 있고, 저장 성공 후 조회 실패를 저장 실패로 안내할 수 있다.
- `apps/web/features/observability/components/AnnotationControls.tsx:16` — 평가가 기본적으로 관련 있음·뒷받침으로 선택되어 있다. 사용자가 검토하지 않고 저장해도 확정 평가가 누적된다.
- `apps/web/features/observability/views/EvidenceQualityView.tsx` — 출처는 텍스트이며 문서로 이동하는 링크가 없다. 현재 연구 주제와 논문을 함께 확인하기 어렵다.
- `apps/web/features/observability/views/EvaluationDatasetView.tsx` — 근거 검토 화면과 같은 입력을 반복하지만 평가 관리·검수·지표 확정으로 이어지지 않는다.
- `apps/web/features/observability/views/OverviewView.tsx` — 미계산 지표가 다수 나열되어 첫 화면의 다음 행동을 가린다. 상태 존재를 보여 주는 카드가 품질 점수처럼 읽힐 수 있다.

### 우선순위 2: 접근성과 레이아웃

- `apps/web/app/globals.css:609` 부근 상태 배지 — 대기·완료·미검증이 같은 시각 스타일이다. 텍스트를 유지하고 상태별 시각적 차이를 보완해야 한다.
- `apps/web/app/globals.css:503` 이후 — 모바일에서는 사이드바 전체가 본문보다 먼저 쌓인다. 긴 논문 제목·출처·탐색 영역에 대한 실제 폭별 검증이 필요하다.
- 평가 입력에는 보조기술용 이름은 있으나 보이는 필드 설명과 판단 기준이 부족하다. “뒷받침”이 무엇을 뒷받침하는지 명시해야 한다.

## 4. 이번에 반영한 변경

- 메뉴: 검토 요약 / 검색 과정 / 논문 근거 검토 / 판단 기록 / 연구자 평가.
- 제목·버튼·상태·평가 선택지 및 API가 제공하는 시스템 용어를 한글로 표시. 기술 식별자와 API 계약은 유지한다.
- 논문 제목·초록·검색어·출처 식별자는 정확한 대조를 위해 원문을 유지한다. 이 원칙을 화면에 안내한다.
- 인공지능 주장으로 오해하기 쉬운 제목을 자동 분류 요약으로, 원문 구절을 수집된 초록 또는 제목으로 변경한다.
- 타임라인을 검색 단계 상태 요약으로 바꾸고 실제 실행 시각 로그가 아님을 안내한다.
- 기록 없음 상태에 연구 주제 검색 링크를 제공한다. 초기 연결 실패 시 계속 로딩으로 표시되던 상태를 구분한다.
- 선택 메뉴의 접근성 상태, 비동기 상태 안내, 처리 중 버튼 문구를 보완한다.

아래의 데이터 모델·집계·기능 재설계는 이번 변경에 포함하지 않았다. 백엔드를 재시작하거나 실제 연구자 평가를 추가하지 않았다.

## 5. 제품 목적과 주요 사용자 작업

**목적:** 연구자가 특정 검색 실행의 결과와 출처를 검토하고, 자동 분류에 동의하거나 수정한 이유를 남길 수 있게 한다.

주 사용자는 연구 주제를 검토하는 연구자다. 운영·평가 담당자의 전체 품질 관리는 별도 보조 화면으로 둔다. 사용자의 핵심 질문은 다음 네 가지다.

1. 어떤 연구 주제를 언제, 어디에서, 어떤 검색어로 검색했는가?
2. 어떤 논문이 왜 관련 있다고 분류됐는가? 원문으로 확인할 수 있는가?
3. 아직 확인하지 못한 연구 조건과 근거는 무엇인가?
4. 내가 검토한 결과가 어디에 저장됐으며, 다음 검토 대상은 무엇인가?

## 6. 목표 화면 구성

| 위치 | 내용 | 주요 행동 |
|---|---|---|
| 공통 상단 | 연구 주제, 실행 선택, 실행 시각·출처·상태, 마지막 갱신 시각 | 실행 변경, 검색 화면으로 이동 |
| 검토 요약 | 수집 논문 수, 검토 완료/전체, 근거 없는 조건, 다음 검토 대상 | 미검토 논문 검토 시작 |
| 검색 과정 | 실제 검색어·필터·검색 범위·오류, 시각이 있는 단계별 기록 | 검색 결과 보기, 부족 조건 확인 |
| 논문 검토 | 논문 목록과 필터, 선택 논문의 원문·분류 이유·조건 매칭 | 원문 열기, 평가 저장 후 다음 논문 |
| 판단 기록 | 판단별 근거 링크, 당시 자동 판단, 연구자 결정과 변경 이유 | 연결된 근거로 이동 |
| 평가 관리 | 주제 범위의 평가 현황, 평가 이력·불일치, 정답 자료 확정 상태 | 평가 검수, 확정 자료 조회 |

논문 검토와 평가 관리에 같은 입력 폼을 중복 배치하지 않는다. 논문 검토에서 평가하고, 평가 관리에서는 저장된 평가를 검수한다. 미구현 지표는 “측정 준비” 접힌 영역으로 이동하며 지표의 의미·계산 조건을 함께 설명한다.

## 7. 단계별 구현 기획과 완료 기준

### 1단계 — 같은 검색을 일관되게 추적

선행 작업: 메모리 저장소를 영구 저장소로 교체하고 기존 실행·근거·평가의 식별자를 보존한다.

- 실행 목록 API와 실행 단위 상세 API를 마련한다. 예: `GET /v1/observability/runs`, `GET /v1/observability/runs/{runId}`. 이는 제안 경로다.
- 모든 수치·논문·평가에 동일한 실행 범위를 적용한다. 주제 전체 합계를 보여 주면 별도 라벨로 구분한다.
- 최신 성공 실행을 기본값으로 선택하고 `?run=…&view=…`로 선택 상태를 보존한다. 상태 코드와 한글 메뉴 이름을 분리한다.
- 부족 조건은 “해당 실행의 조건별 연결 근거 수가 0인 조건”으로 집계한다. 단어 매칭 기반임을 계속 표시한다.
- 조건 미설정, 검색 0건, 실행 실패, 기록 없음, 미검증, 미구현을 서로 다른 상태로 표시한다.

완료 기준: 두 주제·여러 실행을 생성해도 데이터가 섞이지 않는다. 빈 새 주제가 성공 실행을 가리지 않는다. 새로고침·직접 링크·뒤로 가기로 동일한 실행과 메뉴를 복원한다. 서버 재시작 후 기록이 유지된다. 조건 B에 연결된 근거가 0건이면 부족 조건으로 표시된다.

### 2단계 — 원문 확인에서 평가 저장까지 연결

- 논문 제목·연도·출처·초록 여부를 상단에 표시하고 안전한 원문 링크를 제공한다.
- 전체 초록 보기와 분류에 사용한 문장·조건을 구분한다. 초록이 없으면 제목 기반 분류라고 표시한다.
- 평가 필드는 미선택으로 시작하며 “관련 있음/없음”, “연구 공백 반대 후보/연구 필요성 뒷받침/기타”의 판단 기준을 제공한다. 판단 유보 상태 추가는 API 계약과 함께 설계한다.
- 기존 평가를 불러오고 평가자·시각·근거 설명을 보존한다. 저장과 수정의 의미를 구분하고 중복 클릭은 같은 결과가 되게 한다.
- “저장 후 다음 논문”과 미검토 필터를 제공한다. 저장 실패 시 입력 유지, 저장 성공·목록 갱신 실패는 별도 메시지로 표시한다.
- 저장 중에는 해당 카드만 잠그고 검토 대상을 임의로 최신 주제로 변경하지 않는다.

완료 기준: 동일 논문의 평가 수정 시 의도치 않은 중복 기록이 생기지 않는다. 메뉴 이동 전 미저장 입력을 알린다. 원문 확인→평가 저장→다음 논문을 키보드로 수행할 수 있다. 다른 주제의 평가가 집계에 섞이지 않는다.

### 3단계 — 증명 가능한 판단 기록과 품질 평가

- 검색 단계 이벤트에 실행 ID, 시작·종료 시각, 상태, 오류, 입력·출력 수를 저장한다. 실제 이벤트가 없는 단계를 완료로 표시하지 않는다.
- 판단과 근거를 다대다 연결하고 당시 검색 실행·자동 분류 버전·연구자 결정 버전을 보존한다.
- 평가 담당자가 검수한 정답 자료와 모델/검색 버전을 고정한 뒤 지표를 계산한다.
- 재현율은 정답 관련 논문 중 검색된 비율, 정밀도는 반환 결과 중 관련 논문 비율로 정의한다. 순위 지표에는 관련성 등급을 정의해야 한다.
- 검토한 검색 결과만 모으면 누락 논문을 알 수 없어 재현율의 정답 분모로 충분하지 않다. 별도의 정답 수집·검수 절차가 필요하다.
- 표본 수·분모·버전·측정 시각을 지표 옆에 표시한다. 데이터가 없으면 0점으로 처리하지 않는다.

완료 기준: 각 지표에서 사용한 표본과 계산 근거를 재현할 수 있다. 연구자 평가가 늘었다는 이유만으로 정확도 상승을 주장하지 않는다. 각 판단에서 실제로 사용한 근거와 당시 결정을 열 수 있다.

## 8. 사용성 검증 계획

다음은 아직 측정하지 않은 목표다. 연구자 3~5명을 대상으로 작업을 관찰하고 실패 원인을 기록한다.

- 첫 화면에서 현재 연구 주제와 실행 시각을 10초 안에 찾는다.
- 논문 1건의 원문을 열고 관련성 평가를 60초 안에 저장한다.
- 기록 없음·검색 0건·미검증의 차이를 설명할 수 있다.
- 부족 조건에서 관련 논문 또는 재검색 단계로 이동한다.
- 360px·768px·1440px 폭과 키보드만 사용하는 환경에서 메뉴·긴 제목·평가 입력을 확인한다.
- 검색 선택 복원, API 오류, 저장 성공 후 새로고침 실패, 중복 저장, 서버 재시작을 포함해 검증한다.

우선 실행할 범위는 1단계다. 기록 범위를 신뢰할 수 있어야 논문 검토와 품질 평가를 의미 있게 연결할 수 있다.
